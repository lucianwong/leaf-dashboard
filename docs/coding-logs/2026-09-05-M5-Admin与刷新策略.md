# 2026-09-05 M5 Admin 管理页 + M3 刷新策略下发

## 做了什么

完成 Milestone 5（Admin）最小闭环与 Milestone 3 的服务端部分：

**服务端**：
1. 新增 `src/storage.js`：设备注册表 + 显示配置的 JSON 持久化（`storage/devices.json`、`storage/config.json`），原子写（tmp+rename），配置字段读入时钳制合法区间（轮询 60–3600s，全刷 300–86400s）。
2. 设备心跳：status/frame 请求均 `touchDevice`（记录 firstSeen/lastSeen/lastVersion/page），10s 节流落盘。
3. status 下发 `pollIntervalSec`（服务端统一控制轮询节奏）与 `refresh` 策略：按 `fullRefreshIntervalSec` 周期返回 `"full"`（消残影），其余 `"partial"`。
4. Admin API：`GET /api/admin/devices`（设备列表）、`GET/POST /api/admin/config`（配置读写，POST 只取白名单字段）。
5. 新增 `public/admin.html`：设备在线列表（30s 自刷新）、刷新配置表单、各页面 Frame 实时预览。

**客户端（MainActivity.kt）**：
1. 应用服务端下发的 `pollIntervalSec`（钳制 1–60 分钟，默认 5 分钟），失败仍 30s 快速重试。
2. full 刷新钩子 `performEinkFullRefresh()`：收到 `refresh:"full"` 且有新帧时触发——先反射尝试 Onyx/BOOX 墨水屏整刷接口（EpdController 系），全部不可用则退回"白→黑→内容"三连贴图模拟整刷（利用墨水屏驱动对全黑帧的全波形响应）；失败只记日志不影响显示链路。真机效果待实测校准。

### 核心决策

- 不上数据库:单设备/家庭场景 JSON 文件 + 进程内 Map 足够,符合"避免过度设计"原则。
- full 刷新时机由服务端按版本号(分钟)周期判定,确定性触发且多设备一致;客户端只在有新帧时执行整刷,避免无内容闪屏。
- BOOX 专有 API 反射尽力而为 + 全黑帧兜底,双路径都留日志,真机实测后择优固化。
- Admin 无鉴权与 /download 一致(内网信任环境),页面明示勿暴露公网。
